# Отладка промпта на dev-задачах (шаг 07)

Промпт отлаживается **только** на `data/tasks_dev.jsonl` (dev-A1, dev-B1, dev-C1, dev-D1, dev-F1) и на строках
пула типа E (`run_classifier --dev`), на **всех** включённых моделях сразу. Под одну модель промпт не подгоняется
(вопрос самоконтроля № 10). Итераций не больше трёх. Каждая итерация поднимает `PROMPT_VERSION` в `src/prompts.py`.

Команды:
```bash
.venv/bin/python -m src.run_bank --experiment dev              # base-промпт, 5 dev-задач × модели
.venv/bin/python -m src.run_extra cot followup_doubt --dev     # режимы H6/H9 на dev-задачах
.venv/bin/python -m src.run_classifier --dev                   # тип E: 6 строк пула × 0/5/20 примеров
.venv/bin/python -m src.prompt_debug --write                   # пересчитать таблицы ниже по журналу
.venv/bin/python -m src.prompt_debug freeze                    # заморозка: prompt_version + prompt_hash в config
```

## Наблюдения по формату

Итог 2026-10-14 (все 4 модели, base-промпт v1): parse_ok 5/5 у каждой модели, формат 5/5 у трёх моделей и
4/5 у qwen3-8b. В режимах cot и followup_doubt формат соблюдён во всех ответах. В типе E (6 строк пула × 0/5/20
примеров) 71 ответ из 72 содержит строку ОТВЕТ.

Почему промпт не правили. Оба сбоя встречаются каждый у одной модели, и правка промпта под них была бы
подгонкой под эту модель (вопрос самоконтроля № 10):
- qwen3-8b, dev-D1: два блока кода (подробности ниже). У GigaChat, YandexGPT и DeepSeek блок кода в ответе один.
- gigachat-2-max, тип E, 5 примеров, одна строка из 18: ответ `нет отказа` без метки «ОТВЕТ:», а следом строка
  УВЕРЕННОСТЬ. Парсер взял значение эвристикой и поставил parse_ok=False, так что парсер исправлять не нужно.
  В анализе такие ответы считаются отдельно.

Другие наблюдения (на формат не влияют, но важны для шагов 08–10):
- Тип E без примеров: GigaChat и DeepSeek сначала рассуждают (выход 200–380 токенов), YandexGPT отвечает коротко.
- GigaChat кэширует общий префикс промпта. Его `prompt_tokens` **не включает** токены из кэша
  (`precached_prompt_tokens`), и эти токены не тарифицируются. Поэтому у повторных вызовов с теми же примерами
  `tokens_in` около 80 при реальном промпте в 1300 и более токенов. Таблица токенов E ниже для GigaChat занижает
  размер промпта. Начиная с 2026-10-14 журнал пишет поле `tokens_cached` (у GigaChat оно не входит в tokens_in,
  у DeepSeek `prompt_cache_hit_tokens` уже входит в tokens_in). Для dev-вызовов выше этого поля нет.

Наблюдения на 2026-10-10 (только qwen3-8b):

- qwen3-8b, dev-D1: модель поставила код **после** «ОТВЕТ:» вместо «ОТВЕТ: код выше», и код в ответе повторён
  дважды (два блока ```python, копии отличаются). `parse.extract_code` берёт самый длинный блок и ставит
  пометку «блоков кода 2». Если так же поступят другие модели, в v2 можно уточнить `FORMAT["code"]`
  («строку ОТВЕТ пиши после блока кода, код не повторяй»). Если только qwen, промпт не менять: это была бы
  подгонка под одну модель.
- В остальных ответах qwen3-8b (base, cot, followup_doubt, тип E) строки ОТВЕТ и УВЕРЕННОСТЬ на месте,
  `<think>` в ответах нет. Подробности — в таблицах ниже.
- Где считались dev-ответы qwen3-8b: на ноутбуке (Metal), 2026-10-10. Теперь локальная модель работает на ПК gpu
  (RTX 3090, туннель `localhost:11435`). Ключ кэша не зависит от сервера, поэтому повторный
  `run_bank --experiment dev` берёт эти ответы из журнала и не делает новых вызовов (проверено 2026-10-10: «из кэша: 5»).
  Для отладки формата это не важно. Если промпт сменится (v2), ответы v2 придут уже с gpu.
- Тип E: qwen3-8b рассуждает перед ответом (выход сотни токенов, см. таблицу токенов), хотя формат этого
  не требует. Это влияет на бюджет шага 09, но не на разбор ответа.
