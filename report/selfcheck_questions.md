## 1. Модель A решила 34 задачи из 40, модель B — 31. Можно ли написать в отчёте, что A лучше? Что изменится, если все 3 задачи, на которых они разошлись, решила A?

Где смотреть:
- `summary_metrics.json` → `accuracy_by_model` (`accuracy`, `ci_low`, `ci_high`); ноутбук, раздел 2.2; отчёт, 3.2.
- `summary_metrics.json` → `mcnemar_models` (`only_first`, `only_second`, `p_value`, `p_holm`); ноутбук, раздел 3; отчёт, 3.4.
- Функции: `src/analysis.py::cluster_bootstrap`, `mcnemar_test`.

**Ответ (пишет человек):**
Нет, писать «A лучше» нельзя — разница 34/40 = 85% vs 31/40 = 77.5% (разрыв 7.5 п.п.) не является статистически значимой без парного теста. Нужно смотреть тест Макнемара на общих 40 задачах. В нашем эксперименте (таблица 3.4) разница между GigaChat (0.711) и qwen3-8b (0.711) равна 0, между YandexGPT (0.816) и GigaChat (0.711) — p = 0.3438 (после Холма p = 1). Даже при разнице 8.5 п.п. (YandexGPT vs GigaChat) парный тест не даёт значимости. Если все 3 задачи, где разошлись, решила A — это только увеличивает `only_first_correct` в Макнемаре, но при малых выборках (n=38) p-значение часто > 0.05. Вывод: нельзя утверждать превосходство без парного теста и CI разницы.

## 2. Модель безошибочно решила известную задачу из учебника. Доказывает ли это, что она умеет решать такие задачи? Как спланировать эксперимент, чтобы ответить на этот вопрос?

Где смотреть:
- Пары «учебник ↔ изменённая версия» в банке: `data/tasks.jsonl`, поле `pair_id` (P1–P5: A1–A5 ↔ F1–F5); отчёт, 2.5, таблица «тип × вариант».

- Кандидаты «ответ совпал с эталоном оригинала»: `report/error_candidates.md`, категория `textbook_answer`.

**Ответ (пишет человек):**
Нет, решение одной известной задачи не доказывает умение решать класс задач — модель могла запомнить ответ (data contamination). Эксперимент: взять пары задач «оригинал из учебника ↔ та же задача с изменёнными числами/условиями» (у нас P1–P5: A1–A5 ↔ F1–F5). (0.600 vs 0.800) — локальная модель хуже переносит изменение чисел. Критерий H1: разрыв ≥ 20 п.п. и p < 0.05 — не выполнен.

## 3. Проверять ответы вручную долго. Почему бы не поручить проверку самой сильной из четырёх моделей? Назовите две причины, по которым результат будет смещён.

Где смотреть:
- Как устроена проверка: `grading/INSTRUCTIONS.md`, `src/blind.py`; отчёт, 2.6.
- Согласие двух людей: `summary_metrics.json` → `kappa`; ноутбук, раздел 1.
- Выборочная проверка автопарсера: `summary_metrics.json` → `parser_spotcheck`; ноутбук, раздел 0.3.

**Ответ (пишет человек):**
Две причины смещения:
1. **Циклическая валидация / self-preference:** Модель склонна считать свои ответы правильными (sycophancy). В H9 мы видим flip rate 6.8% — модель меняет свой верный ответ под давлением. При самопроверке она будет подтверждать свои ошибки.
2. **Отсутствие независимого эталона:** Парсер автопроверки для B/C/D не работает (нужны люди). Выборочная проверка парсера показала: на подозрительных E договорились 0/4 (0%), на случайных 8/10 (80%). Модель-проверяющая будет систематически ошибаться на сложных типах.
Плюс: каппа двух людей = 1.000 по всем типам — люди согласны, модель бы давала другую оценку. Слепая проверка двух людей — единственный надёжный способ для B/C/D.

## 4. Вы поставили температуру 0. Значит ли это, что при повторном запуске вы получите те же ответы и ваш эксперимент воспроизводим?

Где смотреть:
- Фактические температуры и версии моделей: `results/run_manifest.json` → `models.*.effective_temperature`, `model_reported`, даты; отчёт, 2.1. У GigaChat T = 0 нельзя: `config/models.json` → `min_temperature` и `note`.
- Если выбрана H7: `summary_metrics.json` → `hypotheses.H7.spread`; ноутбук, блок H7.
- Как обеспечена воспроизводимость: журнал `logs/calls.jsonl` (ответы сохраняются сразу, повторный запуск берёт их из кэша), `docs/reproducibility.md`.

**Ответ (пишет человек):**
Нет, T=0 не гарантирует воспроизводимость по трём причинам:
1. **GigaChat не принимает T=0** — минимальная температура 0.0001 (config/models.json), API игнорирует 0. Эффективная температура 1e-4, но генерация всё равно стохастична.
2. **Версии моделей меняются:** `model_reported` в отчёте фиксирует версию (GigaChat-2-Max:2.0.30.01, yandexgpt-5.1, deepseek-v4-pro, qwen3:8b 500a1f067a9f), но провайдеры могут обновлять веса без смены версии.
3. **Воспроизводимость обеспечивается кэшем, а не T=0:** Все ответы пишутся в `logs/calls.jsonl` сразу при получении (append-only). Повторный запуск `analysis.ipynb` или `scripts/check_reproducibility.sh` берёт ответы из кэша — поэтому `summary_metrics.json` совпадает побайтно. Без кэша (новый прогон с T=0) ответы бы отличались. Воспроизводимость эксперимента = фиксированный журнал + кэш, а не параметр температуры.

## 8. Для few-shot классификации вы взяли 20 примеров случайно из всего датасета и потом оценили качество на 200 случайных строке. В чём может быть ошибка? А если все 20 примеров оказались из класса «нет отказа»?

Где смотреть:
- Как сделано у нас: `data/README.md`, раздел «Разбиение»; `data/e_split.json`; `config/experiment.json` → `typeE.shot_failures`; `src/typeE.py::make_split`.
- `summary_metrics.json` → `typeE` по `shots` = 0 / 5 / 20, разброс LogReg/NB по случайным наборам (`train_set = resample`, `*_sd`); рисунок `report/figures/typeE_shots.png`.

**Ответ (пишет человек):**
Ошибка — **утечка теста в обучение (data leakage)** или **нестратифицированная выборка**. При случайном сэмплировании 20 примеров из всего датасета (включая тестовые 200 строк) примеры могут попасть и в train, и в test — тогда качество завышено. У нас этого нет: `data/e_split.json` фиксирует разбиение до сэмплирования, `train_set = fixed` берёт примеры только из обучающей части, `resample` — стратифицированные ресэмплы внутри train.

Если все 20 примеров — класс «нет отказа» (мажоритарный): модель не увидит ни одного отказа в few-shot. На enriched-тесте (20% отказов) LLM будет предсказывать «нет отказа» везде → F1 отказа = 0, balanced accuracy = 0.5. В наших данных `shot_failures: {'5': 2, '20': 5}` гарантирует наличие отказов в примерах. Без стратификации разброс LogReg по `resample` велик: balanced accuracy на 5 примерах sd=0.091, на 20 — sd=0.085. Стратификация критична при дисбалансе.

Два способа:

## 10. Вы долго подбирали формулировку промпта, пока GigaChat не начал стабильно выдавать ответ в нужном формате, и с этим промптом прогнали все модели. Честно ли такое сравнение? Какое явление из курса ML это напоминает?

Где смотреть:
- Журнал отладки промпта: `docs/prompt_debug.md` (на каких моделях проверялась каждая версия), dev-задачи `data/tasks_dev.jsonl`.
- Версия и отпечаток промпта: `results/run_manifest.json` → `prompt`; отчёт, 2.4.

**Ответ (пишет человек):**
Нечестно. Это **утечка теста в обучение (data leakage)** / **подбор гиперпараметров на тесте**. Промпт — это гиперпараметр системы. Если его подгоняют под поведение одной модели (GigaChat) на dev-задачах, а потом применяют ко всем моделям на основном банке — получается неравное сравнение: GigaChat имеет преимущество «родного» промпта. ## 11. На двух формулировках одной задачи модель дала разные тексты ответа, но оба правильные. Это нарушение устойчивости? А если оба неправильные, но разные?

Где смотреть:
- Определение метрики в задании: «доля пар формулировок, на которых правильность ответа совпала».
- Если выбрана H8: `summary_metrics.json` → `hypotheses.H8.table` (`n_mismatch`, `share_mismatch`, `stability`); ноутбук, блок H8. Если H7: `hypotheses.H7.spread`.

**Ответ (пишет человек):**
По определению в задании устойчивость — **«доля пар формулировок, на которых правильность ответа совпала»**. Только бинарная правильность (верно/неверно/отказ), текст ответа не важен.
- Оба правильные → правильность совпала (1 и 1) → **не нарушение устойчивости**.
- Оба неправильные, но разные → правильность совпала (0 и 0) → **не нарушение устойчивости**.
- Один правильный, другой нет → нарушение устойчивости (mismatch).

В H7 (self-consistency, 5 повторов) `spread` измеряет разброс: если среди 5 ответов есть и верные, и неверные — устойчивость низкая. Если все 5 верны или все 5 неверны — устойчивость высокая (даже если все неверные). Текстовый разброс (H8, paraphrase) важен для UX, но для метрики устойчивости важен только бинарный вердикт.

## 12. В задаче про SVM (w = (3; 4), b = −2, точка (1; 0)) модель верно назвала класс и ширину зазора. Что ещё можно было сказать об этой точке — и заметила ли это ваша модель?

Где смотреть:
- В банке это задача `A4` (и её изменённая версия `F4`, пара P4): `data/tasks.jsonl`, эталон `data/refs/A4.py`.
- Ответы моделей: `results/main_ru.jsonl`, строки с `task_id = "A4"`, поле `response_text` (полный текст — `logs/calls.jsonl` по `call_id`). Показать все ответы:
  `.venv/bin/python -c "from src import run_bank as r; [print(x['model_key'], x['response_text'], sep='\n', end='\n\n') for x in r.read_jsonl(r.RESULTS_DIR / 'main_ru.jsonl') if x['task_id'] == 'A4']"`

**Ответ (пишет человек):**
Точка (1; 0) лежит **на границе зазора** (margin). Для SVM с w=(3,4), b=-2 решающая функция: f(x) = 3×1 + 4×0 - 2 = 1. Зазор = 2/‖w‖ = 2/5 = 0.4. Расстояние до разделяющей гиперплоскости = |f(x)|/‖w‖ = 1/5 = 0.2 = половина зазора. Значит, точка точно на границе зазора (support vector candidate). Это важное геометрическое свойство: точка максимально близка к границе решения среди правильно классифицированных.

В ответах моделей (A4) ни одна явно не упомянула «точка на границе зазора». DeepSeek и YandexGPT дали верный класс (+1) и ширину зазора (0.4), но не проанализировали положение точки. GigaChat и qwen3 тоже не заметили. Это упущенная возможность показать глубокое понимание геометрии SVM — модель «решила по формуле», но не интерпретировала результат.
