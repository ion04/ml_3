## AI4I 2020 (тип E)

- **Источник:** AI4I 2020 Predictive Maintenance Dataset, UCI Machine Learning Repository, id 601,
  https://archive.ics.uci.edu/dataset/601/ai4i+2020+predictive+maintenance+dataset (лицензия CC BY 4.0).
  Синтетический датасет, отражающий реальные данные предиктивного обслуживания; автор — S. Matzka, 2020.
- **Как получен:** `ucimlrepo.fetch_ucirepo(id=601)` (ucimlrepo 0.0.7), 2026-10-10.
  Запасной вариант в коде — zip с сайта UCI (`src/typeE.py::UCI_ZIP`).
  Колонки приведены к виду без единиц (`Air temperature`, а не `Air temperature [K]`), идентификатор строки
  назван `UDI`, как в исходном CSV (ucimlrepo называет его `UID`). Больше файл не меняется.
- **Повторить:** `.venv/bin/python -m src.typeE download` (перезапишет файл тем же содержимым).

### Какие колонки используются

Признаки (6): `Type` (L/M/H — низкое, среднее, высокое качество изделия), `Air temperature` [K],
`Process temperature` [K], `Rotational speed` [об/мин], `Torque` [Н·м], `Tool wear` [мин].
Цель: `Machine failure` (1 = отказ).

**Удалены как утечки:**
- `TWF, HDF, PWF, OSF, RNF` — виды отказа (износ инструмента, теплоотвод, мощность, перегрузка, случайный отказ).
  `Machine failure` по построению датасета равен 1, когда произошёл хотя бы один из них. Это разложение
  самой целевой переменной: в момент прогноза оно неизвестно, а модель с этими колонками угадывает цель
  почти без ошибок. Несколько строк не подчиняются правилу (случайный отказ RNF без `Machine failure`
  и наоборот) — посмотреть: `pd.crosstab(df["Machine failure"], df[["TWF","HDF","PWF","OSF","RNF"]].max(axis=1))`.
- `UDI`, `Product ID` — идентификаторы. `UDI` — номер строки, `Product ID` — тип изделия + серийный номер.
  Свойств станка они не несут, а номер строки может коррелировать с порядком генерации данных.

Удаление делает `src/typeE.py::features()`: файл хранится целиком, чтобы источник можно было сверить.

### Разбиение (`e_split.json`)

Индексы — позиции строк в `ai4i2020.csv`, считая с 0 (`UDI` = индекс + 1). Параметры: `config/experiment.json` → `typeE`,
seed — общий `seed`. Код: `src/typeE.py::make_split`, инварианты проверяет `check_split` (и тесты `tests/test_typeE.py`).

- **Тест** (`test`): 200 строк. По умолчанию **обогащён**: 40 отказов + 160 без отказа (`test_mode: enriched`).
  При естественной доле отказов (около 3,4%) в тесте было бы ~7 отказов, и F1 редкого класса считался бы
  по семи строкам. Цена: доля отказов в тесте (20%) не равна реальной, поэтому accuracy на тесте нельзя
  переносить на реальные данные. Константа «всегда нет отказа» при естественной доле считается отдельно
  (`results/typeE_classical.csv`, `eval_set=full`). Альтернатива — `test_mode: natural` (решает человек).
  Строки теста перемешаны (seed): пробный прогон `--limit 20` берёт начало списка, где есть оба класса.
- **Пул** — все строки вне теста. Примеры few-shot и dev-строки берутся только из пула.
- **Few-shot** (`shots`): стратифицированно и вложенно. Набор 20 = 5 отказов + 15 без отказа, набор 5 = 2 + 3,
  это часть набора 20. Порядок примеров в промпте случайный (seed), у набора 5 тот же относительный порядок.
  Почему не случайно: в пуле около 3,4% отказов, и 5 или 20 случайных примеров часто оказались бы одного класса
  (вопрос самоконтроля № 8). Тогда ни LLM, ни LogReg/NB не увидели бы ни одного отказа, и сравнение потеряло бы смысл.
  Вложенность (5 ⊂ 20) нужна, чтобы разница 5 → 20 была эффектом числа примеров, а не другого набора.
  Доля отказов в примерах (40% и 25%) выше реальной — это тоже искажает априорную долю класса, отметить в ограничениях.
- **Наборы для разброса** (`resamples`): ещё 20 пар вложенных наборов того же состава (отдельный seed + 1).
  На них обучаются только LogReg и NB (без API), чтобы показать, насколько качество зависит от выбора примеров.
- **Dev-строки** (`dev_rows`): 6 строк пула (3 отказа + 3 без отказа), не из теста и не из примеров.
  Нужны для отладки промпта типа E на реальных моделях (шаг 07, `experiment=dev`), чтобы не трогать тест.
